## 4. Confirmed finding detail
### Hidden-phone mask is switched off by sending an active_org cookie that names no organization of the user
- Fingerprint: `telefone-oculto/active-org-cookie-desvia-a-pergunta`
- Source: `lib/supabase/server.ts:58`; `lib/supabase/telefone-oculto-fetch.ts:38`; `supabase/migrations/20261114020000_0517_telefone_oculto.sql:25`; `lib/auth/server.ts:76`; `lib/supabase/telefone-oculto-fetch.ts:55`
- Principal: A restricted agent using their own browser session or an HTTP client carrying their own session cookie.
- Conditions: The attacker is a logged-in member of the tenant. Agent or viewer whose membership has ocultar_telefone = true, set by a manager. The attacker sends an active_org cookie whose value is not one of their organizations: any other UUID, or a non-UUID string. Not in support-impersonation mode. The fallback organization (first membership by accepted_at, then organization_id) is the one whose numbers are exposed; for a single-organization user that is their only organization.
- Bounded reproduction (not executed): input Cookie: active_org=00000000-0000-4000-8000-000000000000 (sent alongside the agent's normal session cookie)
- Result: By source reading, not execution: with an active_org value that matches no membership, the mask decision is false while the request is served for the user's first organization, so phone_number is returned unmasked. The committed test cases 'quem não está marcado recebe o número inteiro' and the 404 case assert that the wrapper returns phone_number '+5511999998888' unmodified whenever the RPC answers false or errors.
- Impact / priority: Discloses contact phone numbers of the agent's own tenant to an agent the manager meant to restrict. No cross-tenant data is reached. The same numbers are already reachable by that agent through the disclosed direct-PostgREST limitation, so the added exposure is limited. Likelihood: It takes one edited cookie and no special tooling, but the attacker must be a restricted team member who knows or guesses the mechanism.
- Smallest fix: Do not key the mask decision on a client-supplied value. Simplest: always call fn_eu_oculto_telefone with p_org null, which the function already defines as 'hidden in any of my organizations'. The trade-off is that a user hidden in one organization is also masked in their other organizations. To avoid that, pass the organization resolved by resolveActiveOrg instead. Also treat an RPC failure other than 'function does not exist' (404) as 'mask'. Regression case: a member with ocultar_telefone = true and an active_org cookie set to a random UUID, and separately to 'x', still receives masked phone_number. The existing test's expectation of p_org 'org-1' must be updated.

## 6. Hardening notes
- proxy.ts:145 reads the whole JSON body in the proxy when Content-Length is absent (chunked upload), because a missing header is treated as 0. Only authenticated sessions reach it and Next bounds the buffered body, but a missing or non-numeric Content-Length should skip the check.
- lib/seguranca/entrada.ts:37 uses `pilha.push(...v)`. A JSON array with more elements than the engine's spread-argument limit (reachable inside the 2 MB cap, e.g. an array of single digits) throws RangeError outside the try/catch, and the proxy answers 500 to that authenticated caller's own request. Push in a loop instead and wrap the walk in a try/catch that fails open.
- The proxy JSON guard keys on Content-Type containing application/json and on Content-Length <= 2 MB. A JSON body sent with another content type, or a larger one, skips it and hits the earlier database 500. Not a boundary, but routes that write user text still need their own validation.
- docker-compose.prod.yml:136 and hostgator-setup-kit/_common.sh pin WAHA by version tag (devlikeapro/waha:latest-2026.9.2) while serverless-redis-http, wacalls and asterisk are pinned by sha256 digest. update.sh now moves the whole installed base to this tag, so a digest pin would bind what the CI check in trivy.yml actually tested.
- .github/workflows/trivy.yml scans the WAHA image by a hardcoded literal (devlikeapro/waha:latest-2026.9.2) rather than the $IMG value read from the compose file, so on the next bump the scan can silently keep covering the old version.
- Dockerfile, Dockerfile.worker and Dockerfile.scheduler use floating base tags (node:22-alpine, alpine:3.20) and now `apk upgrade --no-cache`, so two builds of the same commit can differ. Acceptable for patching, but digest-pinned bases with scheduled bumps would make what Trivy scanned match what is published.
- next.config.ts CSP has no script-src or connect-src (deliberate and documented), so it gives no XSS mitigation; the frame, object and base restrictions are the only effect.
- redis:7-alpine and caddy:2-alpine in docker-compose.prod.yml are floating tags with the default pull policy (older than this scope).
- seguranca.yml tails /tmp/app.log into the public job log on failure. Whether the app can log the Anthropic key or request headers there was not traced; worth confirming the logger never prints it.
- lib/agendadas/executar.ts: at send time the worker re-checks the scheduler's membership and role but not whether they can still see the conversation (made private, or reassigned in visibility_mode 'own'). A message scheduled while authorized still goes out in their name after they lose access. Re-evaluating visibility at send time, or cancelling pending rows on reassignment, would close this.
- lib/supabase/telefone-oculto-fetch.ts: besides the cookie issue, any transient RPC failure yields 'not hidden' (fail open, already disclosed). Failing closed on everything except 'function not found' is a small change.
- lib/contatos/telefone-oculto.ts: the mask covers five JSON keys only. Not traced to a response in this run, but worth checking: contacts.wa_lid, conversations.group_chat_id, messages.external_id (WAHA ids embed the chat JID), messages.metadata.group_sender, a contact name that defaults to the number, and any non-JSON response (CSV/text) produced through the session client.
- Hidden phone: filtering or searching contacts by phone through the session client still works for a restricted agent, so a number could be recovered digit by digit by observing which filters match. Consider rejecting phone filters for marked members.
- app/api/v1/equipe/_membros.ts: names in the team chat and its push notifications come from user_metadata.full_name, which each user can change. A member can display a colleague's name in the internal chat. The list also includes invited members who have not accepted yet (no accepted_at filter), so they can be addressed in direct messages.
- app/api/v1/settings/conversas/route.ts and settings/variaveis/route.ts: read-modify-write of organizations.settings without a version check. Concurrent saves can drop each other's keys (integrity, not access).
- lib/messaging/media/upload-validation.ts: reject any media_storage_path containing '.', '..', empty or percent-encoded segments, or backslashes, and match it against a strict `<uuid>/<uuid>/<name>` pattern. Reuse the same check in app/api/v1/figurinhas/route.ts:103 and app/api/v1/messages/[id]/encaminhar/route.ts:77 instead of startsWith(`${orgId}/`).
- lib/contacts/vcf.ts: build each logical line from an array of fragments joined once, decide the quoted-printable state when the line starts rather than re-splitting it, and cap continuation lines and logical-line length. Also stop parsing once 501 cards have been collected, so the row cap bounds the work.
- lib/figurinhas/figurinha.ts: sharp is called without limitInputPixels, so the library default (about 268 megapixels) applies. A 5 MB highly compressible PNG can declare 16383x16383 pixels and cost seconds of libvips CPU per upload. Set limitInputPixels to a few megapixels and reject on metadata width/height before resizing.
- app/api/v1/figurinhas/route.ts and app/api/v1/contacts/import/route.ts: req.formData() buffers the whole multipart body before file.size is checked. Check Content-Length first, or confirm a body limit at the proxy.
- app/api/v1/figurinhas/route.ts:105-107: the 'from conversation' branch downloads the whole stored media into memory before paraFigurinha applies the 5 MB limit. Check media_size_bytes from the message row first.
- app/api/v1/figurinhas/route.ts:73-78 and 133-137: the 200-per-organization cap is count-then-insert, so concurrent uploads can exceed it slightly. This affects only the tenant's own quota.
- app/api/v1/conversations/[id]/figurinha/route.ts:74 and app/api/v1/messages/[id]/encaminhar/route.ts:82: each send or forward copies the object into the destination conversation folder, and the copy stays if the send fails. An agent can multiply a 50 MB file by 5 per request with no aggregate quota. This consumes the tenant's own storage (shared with the instance on a self-host).
- app/api/v1/conversations/[id]/historico/route.ts: the PDF export lays out up to 5000 messages with unbounded body length through @react-pdf/renderer in the request, with wrap={false} on each block. A conversation with very long inbound messages makes this slow and memory-heavy. Cap body length per line in the PDF (the .txt keeps everything) or lower the PDF limit. Behaviour of wrap={false} blocks taller than a page was not checked.
- app/api/v1/conversations/[id]/historico/route.ts:75: one auth.admin.getUserById call per distinct team sender. Bounded by team size, but could be a single query.
- Add an aggregate cap per webchat channel and per organization on new visitors per window (new contacts and conversations), independent of IP and token, and move these counters to the shared Redis limiter so they hold across replicas.
- Derive the client IP from the hop written by the trusted proxy (rightmost untrusted element, or X-Real-IP set by the proxy) rather than the leftmost X-Forwarded-For value; getIp's fallback to 127.0.0.1 puts all header-less requests in one bucket.
- lerCorpoDoBalao only rejects an oversized body up front when Content-Length is declared. For chunked bodies it buffers up to the framework cap before the 8 KB check. Read the stream with a running byte counter and abort at 8 KB.
- The Origin allow-list is a browser-side control only: a non-browser client can send any Origin header. The UI and docs should not present it as protection against scripted senders.
- origemPermitida ignores the scheme, so http://<allowed-domain> is accepted. Consider requiring https outside localhost.
- If an attendant merges a webchat contact into another contact, the visitor's next message creates a second contact and conversation with the same provider_conversation_id. lerDoVisitante's maybeSingle then errors and the widget gets 500. Reuse the existing conversation by provider_conversation_id first.
- A visitor can set any unclaimed email on their own webchat contact, and email is unique per organization. A stranger can therefore pre-claim a real customer's email on a throwaway contact. Consider keeping visitor-typed email in source_metadata only, until an attendant confirms it.
- The visitor token stays in localStorage with no expiry. On a shared computer the next person on the same site sees the earlier chat. Consider an expiry or a 'end conversation' control in the widget.
- lib/chatbot/regex-segura.ts: count every quantifier that can match a variable number of times (`?`, `{n,m}`, `*`, `+`, `{n,}`) toward one small budget, or run tenant regexes in a worker thread with a deadline or on a linear-time engine such as RE2. Add test cases for 'a?'x40+'!' and 'a{0,99}'x25+'!'.
- lib/chatbot/webhook.ts: read the body through res.body.getReader() and stop and cancel at 64 KB; refuse responses whose Content-Length exceeds the cap. The sibling lib/automation/actions/call-webhook.ts belongs to another unit and was not reviewed for the same pattern.
- lib/automation/outbound-ip.ts: the IPv6 link-local test uses startsWith('fe80'), but fe80::/10 runs to febf; the IPv4-compatible form (::a.b.c.d), site-local fec0::/10 and 6to4 2002::/16 are not listed. Low practical reach because IPv6 literals are refused and https is required in production.
- lib/automation/outbound-url.ts and outbound-ip.ts: the check-then-fetch DNS rebinding window remains (declared in the source). In production it is mitigated by mandatory https and certificate validation; with NODE_ENV other than production, http is allowed and the window would reach internal plain-HTTP services. Pinning the validated IP in a custom lookup would close it.
- app/api/v1/chatbot-flows/[id]/estatisticas/route.ts: CSV cells are quoted but a leading `=`, `+`, `-` or `@` is not neutralized. Output labels come from flow text written by a manager of the same organization and are opened by agents or admins in a spreadsheet. Prefix such cells with an apostrophe.
- lib/chatbot/passos.ts and lib/empresa/variaveis.ts: the variable key regex accepts `__proto__` and `constructor`. No pollution is reachable (string assignments only), but `{{constructor}}` expands to built-in function text. Use Object.create(null) maps or Object.hasOwn on lookup.
- lib/inbox/template-vars.ts and the chatbot message substitution put contact- or webhook-derived values into outbound messages unfiltered, by design; lib/chatbot/links.ts documents that links arriving inside a variable are not checked.

Positive patterns: organization always from session/token/path token; RLS + select-only grants on new tables; direct team chat private even from admins by policy; widget renders only through textContent; workflows without pull-request triggers and with contents: read; SSRF guards with no redirect following.
