# Architecture — run-2 (scoped: plan sheet O1–O9 + S1–S8, diff d823c3914..2e656d9bf)

## 1. Product, principals, protected resources
Multi-tenant WhatsApp sales/support CRM (DeskcommCRM fork "ChatAI Online"), self-hosted on a VPS: Next.js 16 App Router + Supabase Postgres (RLS on tenant tables) + WAHA (WhatsApp HTTP bridge) + AI agents with MCP tools. Principals: anonymous internet caller (only `lib/auth/public-paths.ts`); WhatsApp contact and group member (message text/media, push names, `@lid` chat ids); tenant roles viewer(1) < agent(2) < manager(3) < admin(4) (`lib/auth/require-role.ts`, org from cookie via `resolveActiveOrg`); platform admin (`platform_admins`, `scope` full|support_readonly); API bearer `dsk_` via `lib/api/auth-dual.ts` (token path returns the service-role client; the global `proxy.ts` rejects bearer unless the path is in `public-paths.ts`); the AI model acting as `ai_operator` through MCP tools (`lib/agent-engine/edge/crm/mcp-tools.ts`, turn contact bound by the engine); invited colleague (`conversation_participants`, 0544); sector-restricted agent (`own_and_sector`, 0543); cron/scheduler and the host update agent (Bearer `INTERNAL_SECRET`/`INTERNAL_CRON_SECRET`, `lib/auth/cron-auth.ts`, `app/api/v1/system/agent/route.ts`); external web content fetched by prospecting. Protected: per-org contacts/conversations/messages/notes/media, CPF (decrypted on export), AI credentials, the VPS host (update/rollback shell), WhatsApp number reputation, operator AI spend.

## 2. Comparable baseline
Upstream DeskcommCRM (melgarafael): almost every in-scope feature is a hand port of an upstream PR (`docs/chataionline/MAPA.md`). Upstream patterns (dual auth per route, service-role + manual org filter, definer functions with revoke from public/anon, baseline appendix) apply here; fork-only divergences (header `x-chatai-signature`, forced pt-BR, missing upstream tables) are where ports drift.

## 3. Stack, deployment, offline limits
TypeScript 6 / React 19 / Zod 4 / supabase-js; Postgres SQL with RLS; Bash kit `hostgator-setup-kit/*` applies only `supabase/baseline.sql` (install with ON_ERROR_STOP, update without). Compose: app, worker (`tsx workers/agent-worker/main.ts`), scheduler (crond curling `/api/v1/cron/*` with the internal secret), WAHA, redis+srh, caddy/traefik. Host crontab runs `agent.sh` every 5 min (heartbeat → `system/agent` → may run `update.sh --to <version> [--force]`; post-update watchdog auto-rollback). Local bounded execution: sandbox `bin/sb` (no network, read-only mounts, scratch-only writes, limits) runs vitest read-only and an optional throwaway Postgres 16 (`/opt/sbx-audit/pgbase` = Supabase prelude + baseline). Not available: PostgREST/GoTrue/Realtime/Storage, WAHA, browsers, production storage policies, real VAPID/secret values.

## 5. Trust boundaries and strongest visible control
Org isolation: RLS via `fn_user_org_ids()`/`fn_user_role_in_org`; service-role/pg-pool handlers filter `organization_id` from authz (recon found no cross-tenant gap). Role floors: route `requireRole` vs RLS policies (several RLS floors are weaker than routes: `contacts_update_de_atendente` lets agents flip `is_personal`/`ai_opt_out`/`address_book_name`; `jev_router_decisions` readable by viewers). Conversation privacy: `fn_can_view_conversation` (2-arg form has no `is_private` check; used by `exigirControleDaConversa` and restrictive policies). Platform: `system/update` checks only `is_platform_admin` (no scope=full, no MFA) yet dispatches rollback/force to a host shell. AI: tool calls run as `ai_operator`, contact bound to the turn but `crm_set_conversation_sector` takes any `conversation_id` in the org. Storage: bucket `internal-media` private, service-role only, signed URL 60 s; redaction queue checks bucket allowlist + `{org}/` prefix only. Public: app-icon rate limit keyed on client-supplied `X-Forwarded-For`.
